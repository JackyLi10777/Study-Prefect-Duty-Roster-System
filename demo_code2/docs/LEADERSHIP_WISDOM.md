## Wisdom from 2026-27 (LI Chuangjie)

### On Building This System

**Start with school rules, not with code.** The room capacities, AHP constraints,
and fairness principles came first. The code followed. When in doubt about a
feature, I asked: "Does this serve the prefects or just make the code prettier?"

**Fairness is a practice, not an algorithm.** The workload multiplier and fairness
scoring help, but they can't replace human judgment. If a junior prefect is
struggling, give them fewer duties regardless of what the algorithm says. The
tool serves the team — not the other way around.

**Documentation is leadership.** Every hour I spent writing USER_GUIDE_ZH.md,
HANDOVER.md, and ARCHITECTURE.md was an investment in the next Head Study Prefect.
They won't have to start from zero. You're reading this because someone cared
enough to write it.

### On Using This System

**Always back up before importing.** This rule exists because I learned it the
hard way. One CSV import overwrote 2 weeks of carefully maintained prefect data.
The backup saved me. It will save you too.

**The leave adjustment preview is your friend.** Before applying any leave
change, the system shows you the fairness impact. Read it. Sometimes the
algorithm's recommendation is wrong — trust your knowledge of the team.

**Room 202 is closed on Tuesdays and Fridays.** This rule is hardcoded and
tested. If you see assignments there on those days, it's a bug — take a
screenshot and report it.

### On Leadership

**The roster is a covenant, not a schedule.** When you publish the weekly duty
assignments, you're making a promise to 30+ prefects that the distribution is
fair. Take that seriously. Review every assignment before exporting.

**Leave adjustment is a test of character.** It's easy to always assign the
same reliable prefects as substitutes. Resist that. The fairness algorithm
exists precisely to prevent burnout of your best people. Trust it.

**The scripture verse is not decoration.** It's there to remind you — and every
prefect who sees the roster — that leadership is service. When you're frustrated
with the system or overwhelmed by the responsibility, read the verse. It was
chosen for that moment.

## Regenerative Leadership Reflection (Added Iteration 8, 2026-07-01)

### On Systems That Heal Themselves

A system is regenerative when it gives back more leadership capacity, cultural
vitality, and ethical clarity than it consumes. The audit log now persists across
restarts. The Dashboard gently surfaces data drift before it becomes a crisis.
School rules carry their rationale alongside their enforcement. These are small
changes, but they shift the system from "store and enforce" to "teach and renew."

### For Future Head Study Prefects

**The system now remembers.** When you restart the app, the audit log from
previous sessions is restored. You can see what happened before you arrived.
This is institutional memory made operational.

**The system now notices.** The Data Health section on the Dashboard will
gently show you when prefect data needs attention -- missing Chinese names,
duplicate entries, prefects with no available days. It will not alarm you.
It will simply remind you. Fix these when you have time. The roster will work
either way, but it works better with clean data.

**The system now teaches.** Every school rule in the code now includes a
rationale -- an explanation of WHY the rule exists. When you wonder why Room 202
is closed on Tuesdays, or why AHPs have exclusive posts, the code will tell you.
This is how institutional knowledge survives across generations: not merely as
rules to follow, but as wisdom to understand.

### A Question for Your Generation

As you use and modify this system, ask yourself: **"Does this change help the
system give back more than it takes?"** If you add a feature, does it reduce
cognitive load for the next leader or increase it? If you enforce a new rule,
does the code explain WHY? The most important architecture decision is not
technical -- it is whether the system regenerates the leadership culture it
serves.
